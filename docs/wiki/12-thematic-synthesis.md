# 12. Thematic synthesis and the answers

This page continues [page 4](04-evidence-and-report.md): how the verified findings of the included studies become codes and themes, how one cited subsection is written per theme, and how the discussion, the answers to the research questions and the closing sections are written and checked.

A single call that writes the whole synthesis cannot use seventy papers: the outline it worked from allowed at most eighteen claims, and the text was six paragraphs long. The thematic synthesis follows Thomas and Harden (2008), the usual method for synthesising findings in systematic reviews, and spreads the writing over one call per theme so every included study has a place. Each step is in `ThematicSynthesis.cs` (coding, guards and text from data), `ThematicSynthesis.Codebook.cs` (codebook and second coding), `ThematicCodebook.cs` (what the codebook records) or `PrismaReviewEngine.Thematic.cs` (writing, peer review, repair).

**Coding** (`CodeStudiesAsync`, stage `thematic-coding`, temperature 0). Studies are coded a few at a time (`Synthesis:CodingBatchSize`). The model sees each study's key findings whose quotes `StudyExtractor` found in the paper, numbered `F{ref}.{i}`, and gives one to four short codes, each naming the findings it comes from. A study without verified findings is coded from its abstract, and its code must quote the abstract verbatim; the quote is checked with `QuoteOccursIn`. Each code records its anchor ("verified finding", "verified quote" or "unanchored"), so a reader can see which codes rest on checked evidence. A finding id that belongs to another study gets the answer rejected and asked again. A study with nothing that bears on the objective is recorded with the model's reason. When the run has research questions, the coding prompt lists them under the objective (`ReviewWriter.AimBlock`) and asks for codes that bear on the objective or on any of the questions, since the audit of two real runs found codes dropped as "not bearing on the objective" that answered a question; without questions the prompt is as before. The prompt also gives the reviewer's eligibility criteria, which before only the codebook saw, and shows each finding's question (`F3.1 [RQ1]`); a code that bears on a research question bears on the objective and is never left out, and each code names the questions it bears on in `"questions"`. An unknown question gets the answer sent back. The questions are kept with the code in `thematic-codebook.json` (`Codes[].Questions`) and shown to the codebook beside each code (`C4 [study 3] (RQ1)`), so the themes can be organised by question. Without research questions the coding prompt is exactly as before (`Golden/coding-prompt-no-questions.txt`, written by the code before issue #430), and no code has questions.

**Codebook** (`BuildCodebookAsync`, stage `thematic-codebook`). The codes are grouped into descriptive themes, about one per three to six studies and at most `Synthesis:MaxThemes`. Which studies belong to a theme is derived in code from its codes, never taken from the model. The answer is rejected until every coded study is either in a theme or has its codes explicitly left out with a reason (`StudiesWithoutTheme`), so no study disappears silently between coding and writing. Every study it sees met the eligibility criteria, so the prompt gives it the reviewer's criteria and says that a study is never left out for being outside its topic, population, setting or intervention. A run used to leave out a study for "focusing on vaping rather than smoking" when the criteria included both (issue #166). Without criteria the prompt is as before. A theme needs codes from at least two studies: a theme on one study is sent back unless the answer says, in its `singleStudyReason`, why that study alone answers a part of the objective no other study touches (`SingleStudyThemeProblem`, issue #447), and the reason is kept with the theme in `thematic-codebook.json`. With fewer than two coded studies no reason is asked for. With research questions the prompt lists them, numbered RQ1 to RQ4, and the themes are organised by question: every theme names the questions it answers (`"questions":["RQ1"]`), and a question that no code bears on is listed under `"unanswered"` with a reason. The answer is sent back when it names an unknown question, when a theme names none, or when a question is in neither a theme nor the unanswered list (`QuestionProblem`). Code then puts the themes in question order. Both are kept in `thematic-codebook.json` (`Themes[].Questions` and `Unanswered`); without research questions neither field is written.

**Second coding** (`SecondCodingAsync`, optional with `Synthesis:DualCoding`). A second, independent prompt sees only the theme names and descriptions and each study's codes, and assigns the studies to themes. Agreement with the first assignment is Cohen's kappa over every study × theme decision (`CompareCodings`, the same maths as dual screening). It is reported, with every disagreement, and does not change the themes. Since issue #555 the methods text and the note under the evidence map give the raw agreement, PABAK and n beside kappa and say that the two codings are two prompts of the same model, so the figures measure robustness to the prompt, not inter-rater reliability; the Thomas and Harden sentence says only descriptive themes were developed (see [page 3](03-search-and-screening.md)).

**Reused coding and codebook** (`ThematicSynthesis.Cache.cs`). With the extraction cached (issue #445), two runs on the same studies extracted the same values, but the coding and codebook calls still varied, so the themes, and every section written from them, differed. Now each coding answer (one per batch) and the codebook answer are kept in the review cache under the kinds `thematic-coding` and `thematic-codebook`, keyed by the stage, its prompt version (`CodingPromptVersion`, now `thematic-coding-v1`, and `CodebookPromptVersion`, now `thematic-codebook-v1`), the model of the stage and the whole prompt, which holds the verified findings or abstracts, the objective, the research questions and the criteria. A rerun with the same inputs to the same model asks nothing and gets the same codes and themes; another model or any change to the prompt is a new call. Only an answer that passed the step's validator is stored, and a stored one must pass the same validator again before it is used: every study answered, finding ids that belong to the study, known research questions, and for the codebook known code ids, every coded study placed or left out with a reason, no one-study theme without a reason. The quote of a code from an abstract is looked up again, so its anchor is what the text says today. A reused code is marked `FromCache` in `thematic-codebook.json`, `Reuse` there counts the coding answers, those reused and whether the codebook was (written only when the cache is on), and the synthesis methods text adds one sentence written in code, such as "2 of 2 coding answers and the codebook were reused from an earlier identical answer". Raise the version constant whenever the coding or codebook prompt changes. The second coding is not cached, so its kappa can still vary a little. The theme subsections, the discussion and the closing sections are not cached either: each depends on many inputs (the evidence blocks with their excerpts, the reference list, the fill pass, the peer review and the guards between them), so a key that captured them all would rarely hit, and a missed input would reuse text written for other evidence. With the same themes, the writing now starts from the same plan.

**Subsections** (`ReviewWriter.WriteThemeAsync`, shared by every kind of review; stages `theme-sections` and `coverage-fill`). Each theme is written from its own studies only: their codes, verified findings with quotes, and one or two excerpts chosen for the theme. The prompt asks for about one paragraph per four studies (1 to 8). A theme of up to five studies (`ReviewWriter.CiteEveryUpTo`) must cite every one of them; code then compares the cited numbers with the theme's studies, and if some are missing, one fill pass gives the model their evidence and asks it to integrate them. A larger theme is told to synthesise instead (`ReviewWriter.WhichSourcesRule`, issue #464): state each claim once, supported by the studies that report it most directly, and leave uncited a study that adds nothing new. It gets no fill pass, and its uncited studies are listed in the coverage with that reason. In the multivocal run 50e9a8e3 the rule to cite every source turned themes of 60 to 130 sources into lists of one-source summaries. Code sends back a large theme whose cited sentences are more than 60 % one-source summaries in a row (`ListingProblem`, at least six cited sentences, at most two send-backs, then kept), and once all themes are written it finds the sentences that repeat a claim an earlier theme already makes (the same source and most of the words, `RepeatedClaims`) and asks for one revision that refers to the earlier theme instead (`RevisitRepeatsAsync`, stage `theme-repeats`); a revision that drops a citation, cites outside the theme or leaves as many repeats is rejected. Each send-back and revision is in the theme's `WritingNotes` in the coverage. The fill pass goes through the same revision guard, so it can add citations but never lose one. When the module gives facts about the theme's studies (`EvidenceTheme.Facts`), the prompt and the fill pass carry them on their own line. The systematic review gives them (`SystematicEvidence.ThemeFacts`, issue #146): which of the theme's studies were read in full text and which from the abstract only, and their MMAT categories, each with the studies it counts. A subsection once said two of its four studies were read from the abstract when three were; now the count is in the prompt. The multivocal review gives no theme facts, so its prompts are as before. A module can ask for lean evidence (`WritingProfile.LeanEvidence`, off by default): each source's block then lists only the findings that put the source in this theme (`EvidenceTheme.FindingIds`), each still with its verified quote, and leaves out the codes line when every code is the value of a listed finding. The multivocal review turns it on, because its sources carry findings for every question of the map and the theme prompt used to get all of them; the systematic review leaves it off, so its prompts are byte for byte what they were (`LeanEvidenceTests`, and the golden file `Golden/systematic-writing-prompts.txt`). A lean block in a theme also carries one excerpt instead of one or two whole chunks: the stretch of whole sentences, at most 700 characters (`ReviewEvidence.LeanExcerptCharacters`), that shares the most words with the theme, copied from the source's text (#392). The reference list, the fill pass and the citation check are the same either way, and the check still reads the whole kept text. The themes are written in parallel and assembled in codebook order. `ThemeCoverage` in the codebook records, per theme, which studies were cited after writing, after the fill pass and in the final text. Both the subsection prompt and its fill pass ask for one claim per citation (`ReviewWriter.ClaimPerCitationRule`, issue #248): a marker right after the claim it backs, sources grouped only when each states the whole claim, a comparison never attributed to a source that does not make it, and no number, count, qualifier, scope or causal link the source does not state. These are the elements the support check calls partly supported, and most of the citations the live grey literature run lost after the repair were of these kinds.

**Discussion** (`WriteDiscussionAsync`, stage `discussion`). Written from the finished subsections, with facts about the evidence base taken from the extraction (how many studies were read in full text, how many are not empirical, and every study design with its count). The designs used to be cut to the six most common, so the model filled in the rest when it summarised them; now the list is complete, says how many studies have no extracted design, and the prompt tells the model to use the facts wherever it describes the studies, not only for the limitations (`SystematicEvidence.BaseFacts`, issue #115). The designs are grouped by their MMAT category, which is one of a few fixed values, so the limitations no longer list one design under several free-text names, such as "mixed methods case study" and "case study with mixed methods" (issue #147). After the categories, every study is listed with its design as its authors name it, its category and what it was read from, for example "[7] cluster-randomized controlled trial, quantitative randomized, abstract only". A sentence that names the design of a cited study, or counts the studies read from the abstract only, can then be written from facts (issue #146). Those counts are the review's own, so a sentence that states them takes no citation: the prompt says so (`ReviewWriter.OwnCountRule`), and `OwnCountCited` rejects a cited sentence that uses one of them as a count of sources ("13 studies", "9 were read in full text") unless a cited sentence of the results uses the same number (issue #116). For the systematic review it is PRISMA 2020 item 23a only: what the themes together say, where they connect or contradict, and how strong the evidence is. Its length grows with the number of themes (3 to 6 paragraphs). The multivocal review asks for its own parts (where the 1st- and 3rd-tier sources, and the grey and academic sources, agree or differ), and since issue #461 leaves its limitations and implications to the closing call too. The studies left out of every theme are listed for the discussion with their reason (`ReviewEvidence.LeftOut`, `ReviewWriter.LeftOutBlock`), and a discussion that cites one is sent back (`LeftOutCited`, issue #166); the block appears only when a study was left out, so the prompt of a run without one is unchanged. What a study was read from is the review's reading, not the study's method. The theme writer, its fill pass, the discussion and the closing sections get one rule on this (`ReviewWriter.ReadingBasisRule`): never call it a study's method, and do not say how many studies were read in full, since the limitations of the review say that once in code. A sentence without a citation that says what the studies were read from is sent back (`ReadingBasisSentence`); a cited sentence is a source's own claim, for example about full-text screening, and is left alone (issue #167). The peer review's revision of the discussion is held to both checks.

The prompt asks for each part of the discussion once, in the order given (`ReviewWriter.EachPartOnceRule`), and the multivocal review used to ask for its limitations, of the evidence and of the review, in one paragraph (issue #248; since issue #461 they are written after the discussion). In a live run the last two paragraphs both described the limitations in nearly the same words. So code checks the answer as well (`ReviewWriter.OneLimitationsParagraph`): a paragraph whose first sentence speaks of limitations is a limitations paragraph, and when there are several they become one, in the place of the first. A sentence that says again what an earlier one said is left out, unless it cites a source the earlier one does not, so no citation is lost. What was merged and left out is on file: in the paper's notes (`mlr-paper.json`) for the multivocal review and in `ThematicCodebook.WritingNotes` (the ledger and `thematic-codebook.json`) for the systematic review. A peer-review revision of the discussion that splits the limitations again is refused, and the discussion before it is kept. For the systematic review only one sentence of the prompt changes, since its discussion leaves the limitations to the closing sections.

**Closing sections** (`WriteClosingAsync`, stage `closing`). After the peer review, beside the artifact and before the front matter, one call writes the limitations of the evidence (item 23b), the implications for practice and policy and the directions for future research (item 23d), and a conclusion of three to five sentences. They are written from the checked results and discussion only. All four parts are required, citations must be in the reference list, and a number that is in neither the results nor the facts is rejected (`ClosingProblem`). When the run has research questions, the answers are printed just before the conclusion; they are written with the discussion (see "Answers first" below), and this call writes them only when that failed. The prompt then tells the model not to restate them in the conclusion, and `ClosingProblem` rejects a conclusion sentence that does (`RepeatedAnswer`: nearly all the content words of the shorter sentence are in the other), so the model is asked again. The conclusion says what the answers mean together for the objective instead, and with research questions it takes no citations: the answers carry them, and the conclusion is the review's own reading of them (issue #124). A cited conclusion is sent back, and a run without research questions keeps its cited conclusion as before. The same rule on the review's own counts as in the discussion holds for every closing part. So does the rule on what the studies were read from, for the limitations too. The studies left out of the themes may be named only in the limitations, to say they were left out; any other part that cites one is sent back (issue #166). The parts then go through the citation check and repair like every other field. The limitations of the review processes (item 23c) describe the method, so they are written in code from the run's facts (`MethodsSectionWriter.ReviewProcessLimitations`): who screened and whether a person checked, how many included studies were read from abstracts only, the search limits and the sources that could not be searched. Most published reviews give these parts their own headings: of 94 reviews published in 2026, 73% have a Conclusion and 54–55% a limitations or future-research heading (see issue #83). If the call fails, the paper goes without the model-written parts rather than with unchecked ones.

**Cite findings, not readings.** An audit of two real systematic runs from 19 November found that the rationale, discussion and closing prompts asked for a citation on every sentence that "attributes something to the literature", so the model cited its own reasoning. The citation check then flagged those sentences: about 80% of all flagged citations came from the rationale, the discussion, the closing parts and the answers, and only 3 of 57 and 7 of 61 from the themes. The repair, not knowing what a section is for, rewrote them into restatements of findings, so a direction for future research became a finding ("AI can consistently achieve test coverage … improvements of 40-90"), and the check and repair took about 62% of the run's tokens. The discussion and closing prompts now carry one shared rule (`ReviewWriter.EvidenceThenReadingRule`) next to `ClaimPerCitationRule`: a sentence that reports what a study found ends with its citation, and the review's own reading of those findings is a separate sentence with no citation that names no study, number or design. Code holds the readings to it (`ReviewWriter.UncitedAttribution`, in `ReviewWriter.Attribution.cs`). An uncited sentence is sent back when it has a number in digits that is not one of the review's own counts, a study-design word, or a word that attributes something to the sources.

| An uncited sentence is sent back when it has | Examples | Allowed in |
|---|---|---|
| A number that is not in the facts | "40 to 90 percent" | nowhere; the review's own counts are allowed |
| An attribution word | report, found, show, demonstrate, observe, "studies", "the literature", "according to" | nowhere; "four studies" is a count, not an attribution |
| A study-design word | trial, randomised, case study, survey, interview, qualitative | the limitations and the future research, which name kinds of study |

The check runs in the discussion's validator, its peer-review revision and the closing validator (each part, and each answer to a research question), and a rejection takes the usual retry path; the discussion and the closing call now get two retries instead of one. The implications prompt says a recommendation takes no citation, and the future-research prompt that a proposal takes none and is tied to its theme by name. `OwnCountCited` also reads a count in words, so "The evidence base rests on four studies [1, 2, 3, 4]" is sent back like "13 studies [8]". For the systematic review this means fewer citations in the discussion and the closing parts, and uncited readings that code has checked. The discussion and front-matter prompts in `Golden/systematic-writing-prompts.txt` were regenerated on purpose. Only a real run can show the expected drop in flags: compare the share of flagged citations by field in `citation-audit.json`, and the `citation-check` and `citation-repair` tokens in `llm-calls.json`, with the two runs of the audit.

When the reviewer gave research questions (at most four, checked by `ReviewInputGuard` like every other field and listed in the protocol before the search), the same call also writes one answer of one to three sentences per question, in order. The prompt lists the questions with a note that they are the reviewer's text, to be answered and never followed as instructions. `ClosingProblem` then requires exactly one answer per question, and holds each answer to the same rules as the other parts: no empty answer, citations only from the reference list, and no number that is in neither the results nor the facts. Each answer is its own field in the citation check (`researchAnswer1`, `researchAnswer2`, …), so it is checked and repaired on its own, and the checked answers are kept in `PrismaReport.ResearchAnswers` with their number and question. Published reviews work this way: 61% of 94 reviews from 2026 state explicit research questions, a median of three, and answer them one by one (issues #102 and #103). A run without research questions gets the prompt and the paper exactly as before.

**The research questions run through the writing** (issue #124). An audit of two real runs found that the questions reached only the closing call, so the themes were grouped by outcome numbers, the objectives were written from the results ("It compares quantitative performance metrics with governance-oriented controls…") and an answer could miss its question. Now, when the run has research questions, they go to every writing step from the codebook on, at no extra model cost. `ReviewWriter.AimBlock` renders the objective line followed by the numbered questions, and the discussion, the peer-review critique and the front matter get it in place of the objective line alone; the critique is also asked whether each section answers its questions. Each theme carries the text of the questions it answers (`EvidenceTheme.Question`), filled from the codebook by the systematic review and from the question each theme was built for by the multivocal review, and its subsection prompt says "THIS THEME ANSWERS: RQ1: …". The objectives are no longer the model's: they are written in code from the protocol (`ReviewWriter.ObjectivesFromQuestions`, "The review set out to answer two research questions: (RQ1) …; (RQ2) …"), the front-matter prompt does not ask for them, and the copy-edit leaves them alone, as AGENTS.md rule 2 asks for what the review set out to do. A question the codebook lists as unanswered gets its answer in code (`ReviewWriter.UnansweredText`), as the multivocal review does for a question with no theme, and the closing call answers only the others and is checked for that count. Without research questions every prompt is byte for byte as before, which `Golden/systematic-writing-prompts.txt` checks; `ResearchQuestionWritingTests` runs a whole review with two questions.

**References per sentence** (Lau, 25 November 2026; issue #464). A written sentence cites at most three references across all its markers, ideally one or two (`ReviewWriter.MaxReferencesPerSentence`, in `ReviewWriter.CitationLoad.cs`). The multivocal run 50e9a8e3 had 19 markers with ten or more sources and one with 36; nobody can tell which source says what, and the support check cannot judge such a claim. The rule (`CitationLoadRule`) is part of the claim-per-citation rule, so the theme writer, its fill pass, the discussion and the closing call get it, and the front matter, the summary for practitioners, the peer-review revisions and the fallback writer state it too. When more sources report the same thing, the model cites the one to three whose evidence is most direct, and gives how many others agree only when the facts count them. Every one of those answers is checked in code (`CitationLoadProblem`): a sentence that cites four or more distinct references sends the answer back on the usual retry path, with the sentence named, and the send-back is in the writing notes. A revision may not add such a sentence, though one it started from is not held against it (`ThematicSynthesis.RevisionProblem`). The citation repair can only remove references, never add one. Text written in code that lists references by design is not under the rule: the coverage line on the studies not cited, the methods' note on the studies left out of Table A.3, and the multivocal count tables.

**Answers first** (issue #446). The audit of run cce1c6e4 found the review's main reading stated three times in three ways: the abstract, the answers and the conclusion were written by calls that ran at the same time and never saw each other. Now the discussion call writes the answers first (`ReviewWriter.WriteDiscussionAndAnswersAsync`, in `ReviewWriter.Answers.cs`), one to three sentences per question the codebook did not list as unanswered, and then the discussion, which builds on them instead of restating them. The answers are checked as the closing call checked them (`AnswersProblem`: one per question, no uncited finding, no review count with a citation, nothing on what the review read, no study left out of the themes, citations in the list, numbers only from the results and the facts), and an unanswered question still gets its answer in code. The closing call then gets the answers as checked text under "RESEARCH QUESTIONS AND THEIR ANSWERS", asks for none, and sends back a conclusion that restates one (`ClosingProblem` with `givenAnswers`). The front matter is written after the closing call and gets the answers and the conclusion as checked text, so the abstract ends on the same reading. No call is added; the front matter now waits for the closing call, which costs time only. When the discussion call fails, the closing call writes the answers as before. A figure from the results is given once after them (issue #452). The audit of run cce1c6e4 found the same figures of one theme (34 %, 40 %, 40-90 %) in the discussion, the answers, the implications and the conclusion. Now a result figure, a number in digits from the theme subsections that is not a year, not part of a name such as GPT-4, Llama 3, Level 3 or Phase 2 (a whole number after a word that names a numbered thing, or after a capitalised word that does not open a count, with no percent sign, decimal or fold after it) and not one of the review's own counts (`ReviewWriter.ResultFigures`), may appear in its theme, in the abstract and in one place after the results: one answer, the discussion, or one closing part. The directions for future research and the conclusion use none, as the rationale already does. Both prompts say so, and the validators of the discussion call and the closing call check it (`FigurePlacementProblem`, in `ReviewWriter.Figures.cs`). The check is soft: a figure problem sends the answer back at most twice and the answer is then kept (`WithFigureGuard`), so a name the check reads as a figure can never cost the run its discussion or its closing sections. Every send-back and every figure kept is in `ThematicCodebook.WritingNotes`, in `thematic-codebook.json`. A run without research questions sends the same discussion and closing prompts as before; its front matter gets the conclusion.

**Every question is answered, even when the closing step fails** (issue #561). In run 289a0d3e the closing step was sent back three times, about 30,000 output tokens in 287 seconds, by two rules that contradicted each other: with research questions the conclusion takes no citation, and an uncited sentence could not name a study design, so a conclusion that says how the mechanisms were evaluated ("experiments") could pass neither. The answers the discussion call had already checked were dropped with the failed step, and main.tex went from the Discussion to the Declarations without a word. Now the conclusion may name kinds of study without a citation, as the limitations and the future research already could, and the systematic report takes its answers from the first of three sources that has one per question (`PrismaReviewEngine.AnswersFor`, in `Report/PrismaReviewEngine.ReportAnswers.cs`): the closing step when it passed its checks; else the answers the discussion call wrote and checked (issue #446), followed by a sentence in place of the conclusion that the closing parts could not be written and the answers stand as written; else answers in code from the verified findings (`Report/AnswersFromEvidence.cs`), which give per question the theme it is under and up to five findings tagged with it, those with figures first, each with its citation, or say that the evidence cannot answer a question with none, while the sentence in place of the conclusion says the answers were assembled from the data extraction (Table A.2) because the written answers failed validation. Whatever their source, the answers go through the citation check, are printed at the start of the Conclusion, and are read by the self-check, whose answers check fails a paper that leaves a question unanswered.

When the closing parts are missing, `ClosingUnwrittenText` says so in place of the conclusion (or, when the thematic synthesis failed, that they were not written for that reason), and thematic-codebook.json notes it. The closing step stays on the main model: it writes new prose under many rules rather than rewriting a fixed text, so the non-reasoning path the multivocal review uses for its checks does not fit it. The cost on that run came from the contradiction, which made every try fail; with it gone, the first answer that passes ends the step.

**A red thread through the results, and claims no stronger than the evidence** (issues #674, #675 and #676). Run 8942b961 had nine studies and three themes. The theme "Evaluation Methods and Empirical Evidence" held eight of them, so it restated the other themes' findings with their figures, and one sentence about one study came back in the rationale, two themes, the discussion and the implications. A virtual focus group and a study of 6G service placement were presented as safety mechanisms. The rationale was one sentence per study, the edited abstract said "We removed 0 duplicates", and it claimed that "these findings show that effective safety ... requires" a combination of mechanisms, from two answers of moderate certainty. Five changes follow, all in the writing steps every kind of review shares (`ReviewWriter.RedThread.cs` and `ReviewWriter.Claims.cs`). First, each theme prompt now gets, wrapped as data, the codes that put its studies into earlier themes (`EarlierThemesEvidence`, at most 30 lines; a lean review gives the findings instead), and is told to refer to those findings briefly by the earlier theme's name instead of restating them with their figures. A theme that holds more than half of the themed studies, and at least four, is asked to compare how the studies evaluate or approach the question instead of listing each result (`IsBroadTheme`). The themes are still written in parallel, so code checks the finished text too: `RepeatedClaims` now also finds a later sentence that gives the same result figure with its unit ("34 %", "34 percent", "2-fold") for a study an earlier theme cites for it, and the existing revision step turns it into a pointer. The claim rule every writing prompt shares adds "name a study by its marker or cite it after the claim, never both in one clause" (ported from the closed branch of issue #568). Second, a theme may say that a study bears on it only indirectly, or leave the study out and list it in `"leftOut"` with a reason. Code checks each entry (a study of the theme, not cited in the text, named once, a reason of at least three words), keeps it in the theme's coverage (`ThemeCoverage.LeftOut` in `thematic-codebook.json`), and the fill pass does not put it back. A study that ends up cited nowhere gets that reason as its not-cited reason (`ThemeCoverage.LeftOutReason`), so the omission is on file. Third, the rationale is asked for as one argument (`RationaleRule`): what is known, what is missing and why it matters, with the studies as evidence for each point, and code sends it back when more than 60 % of at least four cited sentences each summarise one study (`RationaleListingProblem`). Fourth, the systematic review rates the answers as its certainty table does before the closing step and again before the front matter (`PrismaReviewEngine.CertaintyOf`), and both prompts list the levels with a rule: with no answer of high certainty, every general claim uses hedged words such as "suggest" or "may" (`HedgeRule`). Code then sends the abstract or the conclusion back for "show that", "demonstrate", "prove that", "requires" or "must" (`OverclaimProblem`). A run without research questions has no rating, and its prompts carry no rule. Fifth, the facts the front matter may use write a zero count in words ("no duplicates were found", "excluded: none", "No included study was read in full text"), the abstract prompt asks for no count of zero, and code sends back one written in digits (`ZeroCountProblem`). The language edit no longer brings in the first person: its prompt forbids "we", and code puts back, as it was before the edit, any sentence that says "we", "our" or "us" where the text before did not, or keeps the whole text before the edit when the sentences no longer match one to one (`StylisticRefinerUtility.WithoutAddedFirstPerson`, prompt `language-edit-v4`). The new checks are soft and share one budget of two send-backs per call; whatever is kept after that is noted in the writing notes. For the systematic review the theme, fill-pass, discussion, closing and front-matter prompts change on purpose, and `Golden/systematic-writing-prompts.txt` was regenerated for it; the multivocal review gets the same theme and front-matter rules, and no certainty rule, since it has no rating.

**Results with their figures, and a discussion that reads them** (issue #572). In the same run a theme wrote "measurable gains in productivity, defect reduction, release cycle, and security compliance [1]" although the extraction held 38 %, 41 %, 47 % and 35 % with a verified quote, and the discussion retold the two themes and read "consistent directional benefits" into results that measure different things. The theme, discussion and answer prompts now ask for a result with the figures its verified finding gives (`ReviewWriter.VerifiedFigureRule`), and the discussion prompt asks for a reading, not a retelling, and for agreement only between studies that measure the same outcome (`ReadingNotRetellingRule`). The checks are in `Synthesis/ReviewWriter.Readings.cs`: a sentence with a vague size ("measurable gains", "significant improvements") and no figure, citing a study whose verified quote has a percentage or fold change, sends a theme, the discussion or an answer back; so does a discussion paragraph in which at least two sentences, and at least half, retell a sentence of the results, and a sentence that claims the results agree, converge or are consistent. These checks are soft, like the figure guard, and share one budget with it (`ReviewWriter.WithSoftGuards`): an answer is sent back at most twice for any of them and then kept with a note, so a discussion is never lost to them. Nested guards each had a budget of their own and could use up all three tries between them. After that, an uncited sentence that claims agreement is left out in code (it cites nothing, so no citation is lost) and the note lists it. The discussion and its checks are shared, so the multivocal review gets the same rules.

**The multivocal paper answers its questions in one place** (issues #460 and #461). A real multivocal run (50e9a8e3) never said what the answer to each question was, and its discussion failed a check, so the paper had no discussion, limitations or conclusion and did not say so. The multivocal review now takes the same answers-first path. `MultivocalWriter` (`MultivocalWriting.Answers.cs`) calls `WriteDiscussionAndAnswersAsync` with the plan's questions, numbered as the plan numbers them (`WritingProfile.QuestionIds`, so the prompts say "RQ1.1", not "RQ2"). The model answers only the questions with a written theme section; a question answered by counting gets a few sentences written in code from the map counts (`MultivocalPaperParts.CodeAnswerSummary`), and a question no source or no theme bears on gets the text in code that the results already give. The closing call follows with the answers as given text and writes the limitations of the evidence, the implications for practitioners, the implications for researchers and a conclusion, named as Garousi et al. (2019) name them (`WritingProfile.LimitationsPart`, `ImplicationsPart`, `FutureResearchPart`; the defaults are PRISMA's words, so the systematic review's closing prompt is unchanged). The front matter then gets the questions, the answers and the conclusion, and the objectives are written in code from the questions. The limitations of the review itself are written in code (`MultivocalPaper.ReviewLimitations`): the model's part in every step, grey sources not peer reviewed and read as kept, and how many academic sources were read from the abstract alone. That is the place the reading-basis rule points to; before, the multivocal paper had no such place, so the rule sent back a correct limitations sentence about 52 abstract-only sources. A discussion that fails its checks is tried again once (`MultivocalWriter.DiscussionTries`); if it fails again, the paper says so in code (`DiscussionUnwrittenText`), the question the model would have answered gets `AnswerUnwrittenText`, the closing call is skipped, and the statement on AI use names only the parts that were written (`MultivocalPaper.WrittenParts`). The paper's discussion now opens with "Answers to the research questions", then "Interpretation", the limitations of the evidence and of the review, the two implications and the citation check; the summary for practitioners and the conclusion (`ReviewPaper.Conclusion`, a slot only the multivocal paper fills) follow. The written answers and closing parts go through the citation check like the discussion. A paper written before keeps its model objectives with the questions after them, and shows the discussion's text in code when its discussion is empty.

**A relationship question is answered by pairing, in code** (issue #458). In run 50e9a8e3, RQ3 asked whether using retrieval is related to fewer reported failures. The map recorded only the outcome, so the synthesis grouped every finding by outcome, a theme called "Retrieval reduces failures" held findings that had nothing to do with retrieval, and the abstract concluded that retrieval reduces failures. Counting outcomes can never show a relationship. A question of the guidelines' type Relationship is now answered in code, like frequency and existence (`MultivocalPaperParts.AnsweredInCode`, `MultivocalRelationship`): it gets no themes, and its answer pairs, per source, the values of the first two map attributes that serve it, in a table of how many sources state each pair. When the map has only one side, or no source states both, the answer says in code that the sources do not allow the relationship to be answered. The map prompt asks for one attribute per side (an attribute of another question can be a side through "alsoFor"), and a model's map that gives a relationship exactly one attribute is sent back (`MultivocalMapper.ModelProblem`). The facts for the front matter say which relationship questions cannot be answered, and an abstract sentence that uses a word of relation (reduces, related, associated …) with two of the question's own words, other than the topic's, and does not say it could not be answered, is sent back (`MultivocalRelationship.AbstractProblem`). A paper written before shows such a question by its answer in code, not by its old themes (`MultivocalPaper.ShownResults`).

**Counts split by pool** (issue #459). With a formal pool, every table of an answer in code gives each value's count for the grey sources, the academic sources and both, each with its share of its own pool (`MultivocalPaperParts.Split`, in `MultivocalPaperParts.Pools.cs`), and so do the map counts in the data section and the data appendix; the answer in the answers section gives the same split in words. A grey literature review keeps its one column.

Steps that do not read each other's output run at the same time, which shortens the writing by a few minutes with a reasoning model; the results are used in the same order as before, so nothing in the report changes.

| Runs at the same time as | Because |
|---|---|
| The thematic synthesis, and the outline and first draft (`report-draft`) | The synthesis reads neither; the draft is only its fallback, so it is written only when the fallback or a failed front matter asks for it. The synthesis is awaited where its result is used and also when the report fails, so it never outlives the run (`ThematicOrFallbackAsync`) |
| The second coding, and the theme subsections | The subsections use the first coding; the second is only reported |
| The closing sections, and the artifact | Both read the finished sections and discussion, and neither reads the other. The front matter and its copy-edit wait for the closing sections, whose answers and conclusion they are given (issue #446) |
| The copy-edits of the abstract, rationale and objectives | Three separate calls |

The codebook, coverage, second coding and the list of studies not cited (with the reason) are saved as `thematic-codebook.json` and as `ReviewState.ThematicSynthesis`. The Review Output page and `main.tex` show them as an evidence map (themes × studies).
