# 6. Web app, operations and deployment

The pipeline on pages 2 to 5 runs inside an ordinary ASP.NET Core web app. This page covers the parts around it: start-up, pages and endpoints, the limits that keep the app affordable and responsive, configuration, security, and how a change reaches the live site.

## Start-up (`Program.cs`)

`Program.cs` reads configuration, creates the shared services, and sets up the request pipeline, in that order.

Before anything else it calls `SiteCulture.Apply()` (`Web/SiteCulture.cs`), which sets the invariant culture for every thread. The live server runs in Danish, and without this a page wrote numbers with a decimal comma ("kappa 0,63") while the paper used a point (issue #134). Pages that write a figure with a fixed format still name `CultureInfo.InvariantCulture` themselves, as the paper's code does.

The configuration sections are bound to option classes: `Quota` → `QuotaOptions`, `Runs` → `RunsOptions`, `Llm` → `LlmOptions`, `Cache` → `CacheOptions`, `OpenSources` → `OpenSourcesOptions`, `Synthesis` → `SynthesisOptions` (thematic synthesis on or off, dual coding, citation repair, second citation check, maximum number of themes, studies per coding call), `Metrics` → `MetricsOptions` (metrics store on or off, its folder), plus `Report:SupportStatement` and the API keys (`MISTRAL_API_KEY`, `ELSEVIER_API_KEY`, `IEEE_API_KEY`). The quota service, cache, run options and review engine are created once and registered as singletons; `UiStateContainer` is scoped, so each browser session gets its own. `SessionCleanupWorker` is registered as a hosted background service. Before the app starts serving, `MarkInterruptedRuns` marks runs that were cut off by the previous shutdown.

The request pipeline then adds, in order: forwarded headers (for a reverse proxy, if one is configured), the security headers on every response, the error page and HSTS outside development, HTTPS redirection, static files, antiforgery, the rate limiter, the run downloads (`Web/WorkspaceDownloads.cs`), and finally the Razor components in interactive-server mode.

The dashboard subscribes to `ReviewEngine.OnProgressUpdated` while it is open and unsubscribes when it is disposed. Progress is set by the engine through `ReportProgress` (`RunProgress.cs`): the run's step plan (`ProgressPlan`, with citation chaining and the human review only when asked for), the current step, how far it is from 0 to 1 and a short detail such as "16 of 40 records screened" are kept in `ReviewStats`. `RunProgress.Percent` turns them into an overall percentage using a rough weight per step, and within a step the value never goes back. Updates inside a step are sent at most every 400 ms and do not write the ledger, so loops can report freely. The dashboard also re-reads the saved ledger every few seconds, which can be a little behind the live events; `RunProgress.KeepFurthest` keeps whichever is further along for the same run, so the bar never moves back.

### Read-only links and the edit key

Anyone with a run's link can read it, but only the browser that started the run can change it: delete it, submit its screening review, check a citation again or write notes. When the dashboard starts a run it calls `ClaimRun` (`Runs/RunStore.cs`), which creates a 32-byte random edit key. The browser keeps the key in its local storage (`traceableReview.saveEditKey` in `review-output.js`) and the server keeps only its SHA-256 in `owner.json` in the run folder, which is left out of the archive. Every changing method (`DeleteRun`, `SubmitScreeningReview`, `RecheckCitationAsync`, `SaveNoteAsync`) takes the key and checks it with `CanEdit`, which compares the hashes in constant time. The pages read the key when they open a run and hide the buttons that would change it when the key is missing; the engine refuses either way.

There is deliberately no way to see, copy or restore the key. A key that can be saved can also be forwarded or leaked, and losing it costs little: the run stays readable and expires on its own. Keys older than 30 days are dropped from the browser's storage. Runs started before edit keys existed have no `owner.json` and stay editable by anyone with the link until they expire. A "Copy link" button on the dashboard and the Review Output page copies the run's address for sharing.

### Health, database status and logs

`GET /health` (`SiteHealth.Build`) checks what can be checked without spending anything. **storage**: the run folder can be written to (a probe file is written and deleted) and the drive has room; under 500 MB free is "degraded", under 100 MB "unhealthy". **model**: a model key is configured, or a local model is used; the model itself is not called, since that would cost money on every probe. **source:<name>**: one check per scholarly database the app has asked something since it started, from `SourceStatus`. The answer has an overall status (`ok`, `degraded` or `unhealthy`), the app version, the number of active runs and the checks. It is HTTP 503 only when the app is unhealthy, so an uptime monitor (UptimeRobot, Azure, a cron job with curl) can alert on the status code. It contains no keys, paths or visitor data, and it is kept out of search results.

`SourceStatus` records every request that goes through `OpenSourceHttp`: per host, when it last answered, how long it took, and the last problem (rate-limited, server error, timeout, unreachable, or slower than 10 seconds). A request that only got through after waiting for a rate limit counts as rate-limited. `SourceStatus.Summary()` turns the problems of the last 30 minutes into one sentence ("arXiv is slow (answered in 18 s); Semantic Scholar is rate-limiting requests, so it is slower than usual."), which `SourceStatusNote.razor` shows under the sources on the form and in the progress panel while a run is going. It is kept in memory only and covers all runs on the server.

**Logs.** Every log line written while a run works (engine, sources, cache, model calls) carries the run's ID as a logging scope, opened at the start of `RunReviewAsync`. Outside Development the console log is one JSON object per line with a UTC timestamp and the scopes (`AddJsonConsole`), so a log tool can filter by `RunId`; in Development it stays one readable line per entry. A failed run is logged once as an error, with the exception and the step it stopped in. On the dashboard, a failed or interrupted run shows its run ID and the app version, with a "Report this problem" link that opens a new GitHub issue filled in with the run ID, version and step (`SiteSeo.ProblemReportUrl`), and never with the question or criteria, since issues are public. On IIS the console log is written to files only when `stdoutLogEnabled` is on in `web.config`; turn it on while looking for a problem, and off again, since the files are not rotated.

### Speed and the live connection

- **Static files.** `App.razor` links CSS and scripts through `@Assets[...]`, which gives each file a fingerprinted address that changes when the file changes. `MapStaticAssets` serves them Brotli- or gzip-compressed (compressed at build time) with `Cache-Control: max-age=31536000, immutable`, so a returning visitor downloads nothing again until a new version is deployed. Until issue #301, `app.UseStaticFiles()` ran ahead of it and answered first, without the compressed copies; it is gone, so `MapStaticAssets` serves all of `wwwroot`. Mermaid (3.5 MB) is loaded only when a report has a diagram (`wwwroot/js/mermaid-render.js`). The unused Bootstrap copy was removed from `wwwroot/lib`.
- **Downloads (issue #306).** Every run download under `/api/workspace/{id}/` carries `Last-Modified` and an `ETag` from the run folder's `RunFolderStamp` (`Runs/RunFolderStamp.cs`): a fingerprint of every file's path, size and write time, and the app version. A browser that sends `If-None-Match` or `If-Modified-Since` for an unchanged run gets 304 Not Modified, and nothing is built. The archive of a finished run is kept in its folder as `archive-cache-{stamp}.zip.tmp` (`Report/RunArchiveCache.cs`). It is byte for byte what the builder made, and a later download sends it as it is. A note, a re-check or any other change gives a new stamp, so the next download builds a fresh archive and replaces the kept one. A run that is still going, or stopped part way, is never kept. The `.tmp` ending keeps the file out of the archive and out of the stamp. Measured on a run of 65 files (10.5 MB): building the archive took 232 ms and 65 MB of memory, sending the kept one takes about 3 ms, and a 304 costs the stamp, about 0.2 ms.
- **Metrics (issue #306).** `RunMetricsStore.ReadAll` parses `runs.jsonl` once and keeps the runs in memory while the file's length and write time stay the same; a new run changes both, so it shows at once. The Metrics page asks for the runs several times per view, and so does the model card. Measured on a store of 200 runs (350 KB): a read took about 9 ms and 1.2 MB of memory before, and about 0.04 ms now. With 1,000 runs it was 46 ms; now it is 0.2 ms. Callers get a list of their own but share the run objects, so they must not change them.
- **Following a run (issue #306).** While a run is going, the dashboard looks at its ledger (`transparent-process.json`) every second. `Runs/RunLedgerWatch.cs` parses it only when its length or write time changed and otherwise gives back the last read, so the page shows the same thing. Writing and checking the review do not save the ledger for minutes. Measured on a ledger of 120 studies (0.5 MB), each look cost 7 ms and 3 MB of memory; with 1,200 studies (5 MB) it was 79 ms and 30 MB. An unchanged ledger now costs about 0.004 ms. The report page and the dashboard do not carry what they loaded from the prerender into the live page: that would add the report's data to the HTML (270 KB for 120 studies) and send it back over the connection, to save one read of about 6 ms.
- **The HTML itself is not compressed by the app** on purpose: prerendered pages contain encrypted component state, and compressing secrets together with text a visitor can influence opens the door to BREACH-style attacks. The pages are small (about 30 KB).
- **Text data is compressed as it is sent** (`Web/ResponseCompressionSetup.cs`, issue #301): the run downloads (JSON, Markdown, LaTeX, BibTeX, RIS, plain text), the sitemap and the API's JSON go out with Brotli, or gzip for a browser without it, at the fastest level. HTML and Blazor's connection (`/_blazor`) are left out for the BREACH reason above, and the .zip archive is already compressed. An answer that carries a secret of its own, such as the edit key when a review starts through the API, calls `ResponseCompressionSetup.DoNotCompress`.
- **Lost connection.** `Components/Layout/ReconnectModal.razor` replaces Blazor's grey box with a banner at the bottom that does not cover the page or take keyboard focus, says that a running review keeps going on the server, and offers Try again or Reload when reconnecting fails. Blazor sets the state classes; the styles are in `Styles/tailwind.input.css`.
- **Tab title and notification.** While a run is going, the dashboard's tab title shows its progress ("42% · Your review"), and "✓ Review ready" once it finished while the page was open. "Notify me when it is ready" asks the browser for permission; the notification is only shown when the tab is in the background (`notifyDone` in `review-output.js`).
- **Remembered form.** An unfinished review form is kept in the browser's local storage (`loadDraft`/`saveDraft`, never the API keys) and brought back on the next visit to an empty form, with a "Start empty" button. It is removed when the run starts, and ignored after 30 days. The privacy page says so.
- **Quota messages.** When the free tier or the own-key limit is reached, `RunQuotaService` says when the next run is available ("in 5 h 12 min (midnight UTC)", rounded up) in `QuotaStatus.Message` and `ResetsUtc`, and the dashboard offers to add your own Mistral key.

### Printing a report and the statement on AI use

Review Output has a "Print or save as PDF" button. The print styles (`@media print` in `Styles/tailwind.input.css`, and `print:` classes in `AppLayout.razor`, `LandingLayout.razor` and `SpecMatrix.razor`) release the fixed-height frame so the report flows over A4 pages, hide the top bar, buttons and citation popups, keep figures and table rows from splitting, and add a line at the end with the run id and protocol fingerprint, so a printout can be traced back to its run.

Section 6.4 of every report is a statement on the use of AI, built by `AiUseStatement` only from what the run recorded: the model and app version, the steps the model did, the screening agreement, whether a person checked the screening, and the citation verdicts. Two buttons copy it, or a one-sentence declaration, for a paper or thesis.

When the scan of kept source text (#366) flagged any source, the statement adds one sentence written in code by `AiUseStatement.FlaggedSources` (#363), such as "The full text of 1 of 12 included studies contained phrases that look like instructions to a model; it was flagged for the reviewer and changed no decision." The count is of distinct sources, and the denominator is the sources whose text was kept: for a systematic review the included studies whose full text was read (`ReviewState.FullTextFlags` with at least one flag against `FullTextRetrieved`; a paper that only lost invisible characters is not counted), and for a multivocal review the sources in `multivocal-pages.json` with a kept text (`PageSnapshot.InjectionFlags`), which `MultivocalPaper.AiUse` puts in the paper page's declarations and in `main.tex`. A run with no flags gets no sentence, so its statement is word for word as before. The systematic review's `main.tex` has no statement on AI use, so there the sentence is on the Review output page only.

## Limits: quota, slots, cache

Three mechanisms keep the app affordable and responsive, and they are independent of each other.

`RunQuotaService` decides **whether a run may start**. It has three tiers: *Free* (the server's Mistral key; `Quota:FreeRunsPerDay` per client address, `Quota:GlobalFreeRunsPerDay` across everyone, and at most `Quota:FreeTierMaxResults` results per source), *OwnKey* (the visitor's own Mistral key; `Quota:OwnKeyRunsPerHour`), and *Developer* (a valid `Quota:AdminToken`, no limits). In development every run is unlimited when `Quota:UnlimitedInDevelopment` is true. Counters are stored in `App_Data/run-quota.json`. A run reserves its place with `TryReserve` and gets a `QuotaLease`, which is refunded if the run never starts or fails. A run its owner cancels is given back too, but only once per address and tier per UTC day (`RefundCancelled`, which keeps a `cancelled:` marker in the same file), so cancelling a run near its end and starting again cannot turn one free run into many.

`RunCoordinator` decides **when a started run may use the model**. At most `Runs:MaxConcurrentRuns` runs hold a slot at the same time; the rest queue, and their dashboards show the position. It also holds the gates for runs waiting on a human screening review, and a cancellation token for each live run: `Cancel` takes a queued run out of the line and frees a running run's slot at its next safe point. Everything in it is in memory.

`ReviewCache` decides **whether work can be reused**. Search responses are kept for `Cache:SearchResponseHours` (24) and screening decisions for `Cache:ScreeningDecisionDays` (90), in `App_Data/cache/`. The keys include everything the result depends on, so a changed prompt, model or criterion never reuses an old answer. Reuse is marked per record in the ledger.

Separately, the download endpoints are rate-limited per client address (20 per minute, policy `ArchiveDownloadPolicy`). Runs themselves start over the SignalR connection, which HTTP rate limiting never sees; that is what the quota service is for.

## Clean-up

`SessionCleanupWorker` runs every hour and deletes run folders whose newest file is older than `Runs:RetentionDays`, skipping runs that are still active. It looks at the newest file inside the folder rather than the folder's own date, because the folder date does not change when the ledger inside is rewritten. A kept archive (`RunArchiveCache`) does not count as activity, and neither does the folder date it changes, so downloading a run does not keep it longer. In the same pass, `ReviewCache.Prune` removes expired cache files.

## Security measures

`SecurityHeaders.Apply` adds a strict Content Security Policy (scripts and styles only from the site itself, images from the site and `data:`), `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy to every response. All scripts are served locally: Tailwind is compiled ahead of time into `wwwroot/css/tailwind.css`, and Mermaid is vendored under `wwwroot/lib/mermaid`. User-provided API keys are cleaned with `SecurityUtility.SanitizeApiKey` (only letters, digits and `. _ - :` survive; anything else empties the field) and kept in the browser's protected session storage, not on the server.

The text a reviewer types into the configuration panel goes into prompts, so it is checked by `ReviewInputGuard` before a run starts, both in the dashboard and again at the top of `RunReviewAsync`. The guard normalises every field (Unicode NFKC; invisible and control characters such as zero-width spaces, bidirectional overrides and tag characters removed; the markers the prompts use for third-party text defused), enforces a length limit per field, and scans for instruction-like phrases with the same patterns `PromptSafety` uses for paper text, minus the two that are ordinary in eligibility criteria ("should be included if ..."). Too-long or missing fields are errors; flagged phrases are shown to the reviewer, who can start the run anyway, and are then listed in `protocol.md` and in `ReviewState.InputFlags`. Invisible characters are removed by `HiddenText.RemoveInvisible`, the same way as in source text (see the evidence page), so the rules are the same in both places: a zero-width joiner or non-joiner between two characters outside ASCII stays, so Persian words and emoji sequences are kept exactly as typed, and the tag characters U+E0000 to U+E007F go. Before #380 the guard removed format characters one UTF-16 unit at a time, so tag characters, which are surrogate pairs, got through into the prompts, and the joiners in Persian and in emoji were removed. `ReviewInputGuard.Clean` also returns what the tag characters spelled. When that reads like instructions, `FlagsIn` adds a `hidden-text` flag to the field, last, whose excerpt shows the hidden words after "hidden, not shown in the field:", since the reviewer cannot see them in the box; the hidden text itself never reaches a prompt. The dashboard hands the fields to the engine as typed, and the engine runs the same check, so the flags it writes to the protocol are the ones the reviewer confirmed. Nothing the reviewer typed is rewritten silently; the earlier `SanitizeInput` replaced phrases and stripped anything between `<` and `>`, which also removed text such as "< 5 years". Every prompt that contains the reviewer's fields carries `PromptSafety.ReviewerInputNotice`, and every structured answer is still validated in code, which is what bounds what a prompt can make the model do. Log messages go through `SanitizeLogMessage`, which removes line breaks (against log forging) and anything that looks like an API key. Run folder paths are built only by `GetWorkspaceFolderPath`, which checks that they stay inside the workspace.

The multivocal planning form is guarded the same way (#365). `MultivocalPlan.Normalized` cleans every field with `ReviewInputGuard.Normalize`, and `MultivocalPlanGuard.Flags` scans a cleaned copy of the topic, goal, existing reviews, research questions, criteria and search strings with `ReviewInputGuard.FlagsIn`, the same patterns and exceptions as the form above. What tag characters spelled is read from the plan as typed and matched to the cleaned field it belongs to; a search string that held only hidden text is dropped by the cleaning, and its flag names the list ("Grey search strings"). The hits are listed on the form's last step, and "Start the review" stays off until the reviewer ticks "This is what I meant". `MultivocalPlanner.CreateAsync` works the flags out again, from the plan as typed and before it cleans it, and refuses a plan whose confirmed list differs, so a browser cannot leave one out. The confirmed flags are written under "Input check" at the end of `protocol.md` and in `MultivocalPlan.InputFlags` in `multivocal-plan.json`. Every multivocal prompt that carries the reviewer's topic or questions (the map, extraction, quality and the three synthesis steps) carries `PromptSafety.ReviewerInputNotice`, and `MultivocalPromptNoticeTests` fails when one does not. Their prompt versions were raised with it (`grey-map-v4`, `grey-extraction-v2`, `formal-extraction-v2`, `grey-quality-v3`, `grey-synthesis-v5`), so no cached answer from the old prompts is reused.

The REST API under `/api/v1` is a second way in, off in production until `Api:Enabled` is set. Its requests pass the same input guard, it only runs with the caller's own Mistral key, which is never written to a file or a log, and its calls are rate-limited per key and per address. [Page 9](09-api-and-mcp.md) has the details.

## Deployment

```mermaid
flowchart LR
    PUSH["push / merged PR<br/>to master"] --> BT["Build & Test<br/>dotnet test"]
    PUSH --> CSS["Compiled CSS matches<br/>components"]
    PUSH --> CQ["CodeQL<br/>(separate workflow)"]
    TAG["push a version tag<br/>(release.yml)"] --> REL["check, test,<br/>publish the release"]
    REL --> HEAD{"tag on master's<br/>newest commit?"}
    HEAD -- yes --> DEP
    BT & CSS --> DEP{"DEPLOY_ENABLED?<br/>(deploy.yml)"}
    DEP -- yes --> PUB["dotnet publish<br/>win-x86, self-contained"]
    PUB --> OFF["upload app_offline.htm"]
    OFF --> UP["upload every file over FTPS<br/>(not web.config, App_Data,<br/>WorkspaceStore)"]
    UP --> CHK["check every file's size<br/>on the server, upload again<br/>any that differs"]
    CHK --> ON["delete app_offline.htm<br/>→ new version starts"]
```

The site runs on Simply.com's Windows hosting under IIS. That hosting only has .NET Framework installed, so the app is published **self-contained for win-x86** and runs **out of process** (`AspNetCoreHostingModel` in the project file): with in-process hosting, IIS returned empty static files from the host's network share.

`.github/workflows/deploy.yml` does the deployment, and two workflows call it. `ci.yml` calls it on every push to master, once *Build & Test*, the CSS check and the accessibility check pass and the repository variable `DEPLOY_ENABLED` is `true`. `release.yml` calls it again once a version's GitHub release is published, because the deploy on the push to master ran before the tag existed: that build reads no tag on its commit, so MinVer names it a pre-release (`0.2.1-alpha.0.1`) and its papers say the run used code that "is not a published release". Built again from the tag, the server names the release, v0.2.1. Before that second deploy, a small job asks GitHub which commit the tag points to and which commit master is at, and deploys only when they are the same, so tagging an older commit never rolls the server back; the workflow then shows a note that it did not deploy. Every deploy waits for the one before it, across both workflows. If the deploy for the push to master happens to start after the tag was pushed, it already reads the tag and names the release, so the order does not matter. `tools/ReleaseCheck/test_workflows.py` tests this wiring and the comparison on every pull request.

The deploy job publishes the app and uploads it with `lftp` over FTPS, using the secrets `SIMPLY_FTP_USER` and `SIMPLY_FTP_PASSWORD`. It first uploads `deploy/app_offline.htm`, which makes IIS stop the app and show that page for every request. That page carries everything inline, the reader-bot mark as SVG included, because no other file can be served while it is up, and it follows the visitor's light or dark setting. Then the job uploads every file of the build with `mirror --transfer-all` (never deleting anything on the server and never touching `web.config`, `App_Data` or `WorkspaceStore`). Next, `deploy/verify-upload.py` asks the server for the size of every file of the build, uploads again any file that is missing or has another size, and checks those once more. Only then does the job delete `app_offline.htm`, which starts the new version. A deploy takes about six minutes, most of it the upload. If any step fails, the job fails and the site keeps showing the update page rather than running a half-updated app; re-run the job or delete the file by FTP. lftp runs with `cmd:fail-exit`, so a failed upload really stops the job.

The check was added after an outage on 15 October 2026. The server held empty copies of .NET runtime files (`System.Runtime.InteropServices.dll`, `Microsoft.Win32.Registry.dll`), the mirror took them as unchanged and kept them on every deploy, and the app could not start (HTTP 502.5). After a build made on a developer's machine was uploaded by hand to recover, the next deploy failed the same way: the mirror skips a file whose copy on the server has the same size and a newer date, and .NET's runtime files carry their package's old date, so the server kept a mix of two .NET patch versions. Since then every deploy uploads every file (`--transfer-all`), and the size check stays as a second line of defence. If that ever happens again, turn on `stdoutLogEnabled` in the server's `web.config`: the log in `logs\` names the file .NET could not load. Then upload a fresh `dotnet publish -c Release -r win-x86 --self-contained true` over the site with `app_offline.htm` in place, leaving `web.config`, `App_Data` and `WorkspaceStore` alone, and switch the log off again.

The CSS check exists because Tailwind only includes classes that literally appear in the components, including words in ordinary text. If you change a component, run `npm run build:css` in `AuBtechReviewAgent` and commit `wwwroot/css/tailwind.css` with it. `codeql.yml` scans C# and JavaScript on every push; `release.yml` runs when you push a version tag such as `v1.2.0` and creates a GitHub release, which Zenodo archives when that integration is switched on (see Versions below); the "Release check and changelog" job tests that release check and the repository's `CHANGELOG.md` and `CITATION.cff` on every pull request; Dependabot proposes dependency updates, which pass through the same checks. Tailwind 3 still asks for version 6 of `postcss-selector-parser`, which has a known flaw, so `package.json` overrides it with version 7.1.6 or later; the CSS it builds is the same byte for byte. Remove the override when Tailwind is upgraded.

## Versions

A version is set in one place only: a git tag `vMAJOR.MINOR.PATCH`, following Semantic Versioning 2.0.0. At build time MinVer reads the last tag (`MinVerTagPrefix` is `v`) and the SDK adds the commit after a plus sign. A build on a tag is that version, `0.2.0+40b00a0…`. A build after it is a pre-release of the next patch, `0.2.1-alpha.0.3+…`, where the last number counts the commits since the tag, so a run made on unreleased code never borrows a release number. Before the first tag, builds are pre-releases of 0.1.0 (`MinVerMinimumMajorMinor`). MinVer needs the history, so every checkout in `ci.yml` and `release.yml` uses `fetch-depth: 0`; a shallow clone gets a wrong version with a warning. While the version starts with 0, the method and the output may still change between minor versions; 1.0.0 is kept for the version the OSSYM paper describes.

`RecordingChatCompletionService.AppVersion` is where the app reads the version, and `ToolVersion` (`Runs/ToolVersion.cs`) is how it shows and cites it. The run ledger, `llm-calls.json`, `manifest.json`, `run-metrics.json` and `/health` keep the full string. The Metrics page shows "v0.2.0 (40b00a0)". The paper's availability statement names the version and the commit and links to the release page (`/releases/tag/v0.2.0`), or for a pre-release to the commit, saying it is not a published release; the statement on the use of AI gives the version number. Runs made before versioning keep their 1.0.0 in their own files.

### Publishing a version

A release is published by pushing an annotated tag whose message is its title: `git tag -a v0.1.0 -m "Research questions"` gives the release "v0.1.0 - Research questions". Before that, a `(docs): ` commit on master turns `## [Unreleased]` in `CHANGELOG.md` into the version's section and sets `version` and `date-released` in `CITATION.cff`, so GitHub's "Cite this repository" names the version a run used. `release.yml` first runs `tools/ReleaseCheck/release_check.py`, which stops the release with every reason it found when the tag is not `v` and a Semantic Version, is a lightweight tag or has an empty message, when `CHANGELOG.md` has no section for the version, when `CITATION.cff`'s version or date does not match the tag and the day it was made, or when the notes break the house style for release notes. The checkout is told to fetch the tag again by name, because otherwise it can lose the tag's message. Then the tests run, and the release is created with the changelog section as its notes, followed by GitHub's list of merged pull requests and the comparison link. A version with a pre-release part, such as `v0.2.0-rc.1`, is marked as a pre-release. The steps for maintainers are in `CONTRIBUTING.md` under "Publishing a version".

| What | Where |
|---|---|
| Title | The first line of the annotated tag's message |
| Notes | The version's section of `CHANGELOG.md`, then GitHub's generated notes |
| Citation | `version` and `date-released` in `CITATION.cff`, checked against the tag |
| Archive and DOI | Zenodo archives every release, from `.zenodo.json`, and gives it its own version DOI |
| Concept DOI | `10.5281/zenodo.24379094` in the README badge and as `doi` in `CITATION.cff` |

Zenodo gives the software two kinds of DOI, and they do different jobs. The concept DOI, [10.5281/zenodo.24379094](https://doi.org/10.5281/zenodo.24379094), stands for every version and always opens the newest one. It is the DOI in the README badge and in `CITATION.cff`, and the one to give when you mean the software in general. Each release also gets a version DOI of its own, made by Zenodo when the release is published, so nothing has to be changed in the repository for it. v0.1.0 is [10.5281/zenodo.24379095](https://doi.org/10.5281/zenodo.24379095). A paper that needs the exact version a run used should cite that version's DOI, which is on its Zenodo record.

Release notes are written for someone running a review, not for developers. They say what changed and why it helps, in short plain paragraphs, and may be a bit playful. Two of the rules are checked in code, and the rest by the person who reviews the pull request. Because `[Unreleased]` becomes the next version's notes, CI checks it on every pull request too.

| Rule for the notes | Target | Checked by |
|---|---|---|
| Readability | Flesch Reading Ease of 60 or more (plain English) | `release_check.py` |
| Emoji | Exactly one | `release_check.py` |
| Content | What changed, and why it matters for a review | Review by eye |
| Tone | Everyday English, a bit playful | Review by eye |
